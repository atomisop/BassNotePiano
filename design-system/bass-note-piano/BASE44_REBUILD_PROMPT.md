# Bass Note Piano — Complete Rebuild Specification (for Base44)

## 0. Read this first — how to use this document

This is a **functional specification**, not source code. It was generated by reading every file of a working Next.js + Prisma + PostgreSQL + NextAuth application (~100+ shipped features across many build sessions) and documenting exactly what it does: every screen, every button and its exact label, every validation rule, every data field, every business rule, every piece of copy, every animation value.

**What this document cannot do:** hand you the literal React/TypeScript/Prisma source and have it run inside Base44. Base44 generates its own implementation (its own database, its own auth system, its own frontend code) from a natural-language description — it doesn't import and execute someone else's codebase. So treat everything below as **the spec to build toward**, not literal code to paste in.

**How to use it with Base44:** paste this whole document as your starting prompt, or work through it section by section (Base44 will likely handle it better broken into a few prompts — start with §2 Data Model + §3 Auth, then layer in §4–§8 as separate follow-up prompts once the foundation exists). Whenever a business rule, an exact copy string, a validation message, or a numeric constant is given below, treat it as authoritative — these were pulled directly from the working app's source code, not guessed.

**One explicit decision point before you start:** the original app's entire payment system is **manual** — a student sends money via Zelle (a US bank-to-bank transfer service) outside the app, types in a confirmation code, and a human admin reviews and approves/rejects it. There is no Stripe/payment-processor integration anywhere. Decide up front whether you want Base44 to rebuild this exact manual-review flow, or whether you'd rather use a real payment processor instead — that changes a meaningful part of §6.

## 1. Product Overview &amp; Design Philosophy

**What it is:** "Bass Note Piano" — a paid online curriculum teaching Ethiopian scales (the kiñit system: Tizita, Bati, Anchihoye, Mixolydian pentatonics) with correct spelling in every key and native chords mapped per scale, delivered as an interactive web app companion to a physical curriculum book. Built for piano/keyboard but explicitly markets its theory as instrument-agnostic (guitar, violin sections on the homepage).

**Pricing model:** one-time $99 payment unlocks the entire 6-scale curriculum for life (no subscription). Optional add-on: $50 per 30-minute live 1:1 lesson (Online or In-Person), 20% off when booking 2+.

**Core user journeys:**
1. A visitor lands on the marketing site, registers, verifies email, gets onboarded, buys curriculum access, and works through 6 scales in sequence — each scale has video/PDF lessons, a practice checkbox, and a quiz; passing unlocks badges and streaks.
2. A student can add friends, message them 1-on-1 or in group chats, and register for in-person classes.
3. An admin reviews and approves payments, manages users/roles/curriculum access, uploads lesson content (video/PDF), manages live-lesson bookings, and reviews class registrations — all from a dedicated admin panel with three independent layers of access control.

**Visual identity in one sentence:** dark, cinematic, photography-led glassmorphism — every screen sits on a full-bleed warm/desaturated photo (piano keys, guitar, violin, sheet music, vinyl), with frosted "real glass" panels floating on top, one amber accent color, serif headings + sans body text, and spring-physics motion throughout. Full spec in §9.

## 3. Auth &amp; Account System

### 3.1 The verification-code engine (used everywhere — build this once, reuse for all 6 purposes)

- 6-digit numeric code (000000–999999), hashed at rest, never store raw.
- Expires in **exactly 10 minutes**.
- **Maximum 5 wrong attempts** before the code is force-invalidated.
- Issuing a new code for the same (email, purpose) immediately invalidates any other still-open code for that pair — only the most recent is ever valid.
- Two issuance modes: (a) emailed to the user normally, or (b) issued "silently" (never emailed) when trust was already established another way in the same request — used to auto-log-in a user right after they verify their email or reset their password, without a second round trip.
- The 6 purposes: EMAIL_VERIFY, LOGIN_2FA, PASSWORD_RESET, CHANGE_PASSWORD, CHANGE_NAME, CHANGE_AVATAR. A code for one purpose can never be replayed for another.
- For CHANGE_* purposes, the pending new value (new name / new password hash / new avatar) is staged in the code record and only actually applied once the code is confirmed — never applied optimistically.

### 3.2 Email delivery

Every transactional email shares one template: amber gradient top bar, "Bass Note Piano" wordmark, title, body, footer note "If you didn't request this, you can safely ignore this email." Code emails show the 6-digit code in a large letter-spaced monospace block, always followed by "This code expires in 10 minutes."

Exact per-purpose subject / heading / intro copy:

| Purpose | Subject | Heading | Intro |
|---|---|---|---|
| EMAIL_VERIFY | "Verify your email — Bass Note Piano" | "Confirm your email" | "Welcome to Bass Note Piano. Enter this code to verify your email and finish creating your account." |
| LOGIN_2FA | "Your login code — Bass Note Piano" | "Confirm it's you" | "Enter this code to finish logging in." |
| PASSWORD_RESET | "Reset your password — Bass Note Piano" | "Reset your password" | "Enter this code to choose a new password." |
| CHANGE_PASSWORD | "Confirm your password change — Bass Note Piano" | "Confirm password change" | "Enter this code to confirm you'd like to change your account password." |

### 3.3 Registration — `/register`

- Eyebrow: "Start learning". Heading: "Create an account".
- Fields: Name (required), Email (required, valid format), Password (required, min 8 chars — client copy: "Password must be at least 8 characters."), Confirm password (must match — client copy: "Passwords don't match.").
- Button: "Create account" → "Creating account…" while submitting.
- Footer: "Already have an account? Log in" → `/login`.
- Server errors: "Enter a name, a valid email, and a password of at least 8 characters." (validation) / "An account with that email already exists." (duplicate).
- On success: account created (unverified), a 6-digit EMAIL_VERIFY code is emailed, user is sent to `/verify-email?email=...`. **No session is created until email is verified.**

### 3.4 Email verification — `/verify-email`

- Missing-email state: "Missing email. Start over" → `/register`.
- Normal: eyebrow "Almost there", heading "Verify your email", subtext "We sent a 6-digit code to **{email}**."
- Field: 6-digit code, numeric-only, centered, monospace, auto-focus.
- Button "Verify" (disabled until 6 digits) → "Verifying…". Secondary button "Didn't get a code? Resend".
- Error copy by failure reason: not_found → "We couldn't find an active code for this email. Request a new one below." / expired → "That code has expired. Request a new one below." / too_many_attempts → "Too many incorrect attempts. Request a new code below." / incorrect → "That code isn't right. Double-check and try again."
- On success: marks email verified, **immediately logs the user in** (silent 2FA code, auto sign-in), redirects to the original destination.

### 3.5 Login — 2-step wizard — `/login`

**Step 1 (password):**
- Eyebrow "Welcome back", heading "Log in".
- Fields: Email, Password (with an inline "Forgot?" link to `/forgot-password`).
- Button "Continue" → "Checking…".
- Error (deliberately generic, same message whether email or password is wrong, to avoid leaking which one): "Invalid email or password."
- Footer: "New here? Create an account" → `/register`.
- If the account's email isn't verified yet, this step redirects to `/verify-email` instead of advancing.
- If the device has a valid, unexpired "remember me" cookie for this exact user, **the code step is skipped entirely** — login completes immediately.

**Step 2 (code) — shown only for untrusted devices:**
- Eyebrow "Confirm it's you", heading "Enter your code", subtext "We sent a 6-digit code to **{email}**."
- Field: 6-digit code.
- Checkbox: "Remember me for 7 days" (unchecked by default).
- Button "Log in" → "Logging in…". Row below: "Back" (returns to step 1) / "Resend code".
- Error (generic): "That code isn't right or has expired."
- On success with "remember me" checked: sets an httpOnly cookie good for 7 days that skips the code screen (not the 2FA mechanism itself, which always runs server-side) on this device for this user.

**Hard rule: 2FA runs on every single login, no exceptions** — "remember me" only skips *showing* the code-entry screen to the human; the server still silently issues and consumes a code every time.

### 3.6 New-location login detection

- On every successful login, IP is geolocated (city/region/country); compared against every prior login's location for that user.
- The very first login ever for an account is never flagged (no baseline to compare against yet).
- If the location doesn't match anything seen before, an email alert is sent (see §3.2). **This is email-only — there is no in-app banner, warning, or UI element for it**, and it never blocks the login.

| 5 | "Your goal" | single-select | Learn theory &amp; scales, Master rhythm &amp; chords, Prepare for a performance, Just for fun (hobbyist) |

### 3.11 Cross-cutting rules to enforce exactly

1. Every code expires in 10 minutes, max 5 wrong attempts, only the newest code per (email, purpose) is valid.
2. 2FA is mandatory on every login without exception.
3. "Remember me" = 7-day httpOnly cookie, fixed expiry, no sliding renewal.
4. Password reset AND password change both revoke all trusted devices.
5. New-location detection fires on every login except the account's first-ever; email-only, never blocks, never shown in-app.
6. Forgot-password and resend flows never reveal whether an email is registered.
7. Minimum password length is 8 everywhere; bcrypt cost 12 (or equivalent strength) everywhere.
8. Onboarding is mandatory and blocking, enforced globally.

## 4. Progression, Gamification &amp; Course Player

### 4.1 Access gating logic (the heart of the whole product)

Every scale group resolves to one of three states for a given user:
- **"unlocked"** — this specific scale was granted individually (legacy per-scale purchase or admin override).
- **"curriculum-access"** — the user has the blanket $99 unlock; this bypasses sequential gating entirely, they can jump to any scale.
- **"locked"** — neither; the only path forward is buying the $99 curriculum (there is no way to buy just one scale anymore).

**Sequencing rule:** a curriculum-access holder jumping ahead of "the next scale after their highest completed one" gets a soft confirmation modal (not a hard block) — see §4.3. A scale that's individually unlocked or that the user already has curriculum access to is never hard-blocked by sequence; only a total absence of access is a hard block.

**Quiz pass threshold: 80%** (score/total ≥ 0.8).

### 4.2 The roadmap screen (`/dashboard`)

Vertical connected-path list, one row per scale, staggered entrance animation. Each row = a step marker (checkmark if completed / lock icon if locked / step number in an amber ring if in-progress / step number in a neutral ring if available) connected by a dotted vertical line to the next, plus a card showing:
1. Header: scale code (e.g. "SCALE 3") + a status pill (Locked / Not started / In progress / Completed, with matching dot colors: slate / slate / amber / emerald).
2. Scale title (serif) + kiñit name if present.
3. Three small checklist dots+labels: **Read**, **Practice**, **Quiz** (amber if done, dim if not).
4. A CTA line, with this exact priority logic:
   - if the click needs the "skip ahead?" confirmation → **"Unlock ahead"**
   - else if hard-locked → **"Unlock full curriculum — $99"**
   - else if completed → **"Review"**
   - else if in-progress → **"Continue"**
   - else → **"Start"**

Every card is clickable, including locked ones — clicking a locked card routes straight to the $99 purchase page (every locked card doubles as a soft upsell).

**"Skip ahead?" confirmation modal** — shown when clicking a curriculum-access holder's out-of-sequence scale: eyebrow "Curriculum access", title "Skip ahead?", body "Are you sure you want to unlock {scale code} even though you haven't unlocked the levels before it?", buttons "Go back" / "Confirm override" (→ "Unlocking…" while submitting).

### 4.3 Quiz generation — build this to be deterministic

Given a scale, the quiz question set must be **fully deterministic** (same questions, same order, every time) so the server can regenerate the exact quiz from nothing but the scale id when grading a submission — never trust a client-submitted "correct answer."

- 6 questions per quiz.
- Two question types per scale variant: (a) "What is the scale-degree formula for {variant name}?" with the correct formula + 3 wrong formulas from other scales as distractors; (b) "In the key of {root}, what is the {degree} of {variant name}?" cycling through a fixed list of 6 keys (G, D, Bb, F#, Eb, A) and testing correct note-spelling at each degree, with wrong spellings as distractors.
- Multi-variant chapters (e.g. Scale 3 has Bati Major/Minor/Lydian) round-robin questions across variants so no single variant dominates a 6-question quiz.

**Quiz modal flow:** progress bar segments per question → choice buttons → "Next"/"Submit quiz" (last question, → "Grading…"). Result screen: animated checkmark (pass, emerald) or X (fail), a count-up animated score number, "{score} of {total} correct" + contextual copy, a scorecard chip "Your score: {score}/{total} · 80% required", and on fail a "Retake quiz" button alongside "Done".

### 4.4 Checklist mutations — exact business rules

- **Module read**: satisfied automatically once every uploaded lesson for that scale has been completed by the user (see §4.6) — the old manual "mark as read" button is retired in favor of this. A scale with zero uploaded lessons never auto-completes this (no vacuous completion).
- **Practice completed**: a simple one-way toggle the student clicks themselves.
- **Quiz passed**: every attempt (pass or fail) is logged to history; a fail never un-passes a prior pass; passing the quiz does **not** by itself unlock the next scale — only curriculum access or an individual scale unlock does that.
- **Status derivation**: LOCKED (n/a here) / AVAILABLE (nothing done yet) / IN_PROGRESS (something done) / COMPLETED (all three checklist items true) — recomputed after every mutation.

### 4.5 Course player screen (opens when a scale is clicked)

**Hero card:** scale code, title, kiñit name, description, a primary CTA button (same label logic as §4.2), a "Mark practice completed" pill (turns into a disabled "✓ Practice completed" once done), and a progress strip — one small pill per lesson plus one for the quiz, filled amber as each completes, with a "{n} / {total} complete" caption.

**Course Sections list** (staggered entrance): one row per uploaded lesson, in order, each showing: type icon (video/PDF), title, duration if known, a "Required" tag, and a status:
- **completed** — emerald checkmark, shows "Completed" (or a score, for the quiz row).
- **ready** (unlocked, not yet done) — amber "Start" pill, clickable.
- **locked** — dimmed, not clickable, shows why: `Complete "{previous lesson title}" to unlock.`
- **coming-soon** (only when a scale has zero uploaded lessons at all) — visually distinct from locked (no lock icon), text "Content for this section is on its way.", never blocks anything after it.

Lessons unlock **strictly in sequence** — lesson N only opens once lesson N-1 is marked complete. A final **"Final Assessment"** row always appears last, gated behind every lesson being complete (or unlocked immediately if the scale has zero lessons), opening the quiz modal from §4.3.

**Lesson player (opens in place of the list):**
- *Video*: a real custom control bar — play/pause, ±15 second skip buttons, a seek scrubber, volume slider + mute, elapsed/total time, fullscreen toggle, title/subtitle overlay. **Deliberately no captions or settings button** (nothing real to back them). Completing = the video reaching its end (native "ended" event) OR a manual "Mark as complete" fallback link.
- *PDF*: an inline embedded viewer with a "open in new tab" fallback for browsers that can't preview inline. Completing = simply opening/mounting the lesson (no read-tracking, no scroll-to-end requirement).
- A "← Back to sections" link returns to the list.

**Section-complete celebration screen** (shown right after finishing a lesson): centered panel, animated checkmark, glow-pulse effect, "Congratulations!" / "You've finished this section.", buttons "Course Details" (back to list) and, if there's a next lesson, "Next Section" (jumps straight into it).

### 4.6 Course content data model recap (see §2.3) — key behaviors

- New lessons always append to the end of a scale's list (next order = last + 1).
- Admin can reorder lessons via up/down arrows (see §7.8) — this must never be able to produce two lessons with the same position for one scale at the same time.
- Deleting a lesson deletes its underlying file too (best-effort — don't let a storage-delete failure block the database delete).
- A lesson is "complete" for a user the instant a `LessonProgress` row with a timestamp exists — idempotent (re-watching a finished video is harmless).

### 4.7 Gamification — streaks

- A practice-streak counter increments by 1 whenever the user does *any* tracked activity (reading a module, completing practice, attempting a quiz) on a new calendar day.
- Doing multiple tracked things on the same day only counts once.
- A gap of exactly 1 day (yesterday → today) extends the streak; any other gap (2+ days, or first activity ever) **resets the streak to 1**, not 0 — today's own activity still counts as day one of a new streak.
- Track `currentStreak` and `longestStreak` (the max ever reached) separately.

**Streak visualization:** last 7 calendar days as small circles with day-of-week letters (S M T W T F S), filled amber for the most recent N days matching the current streak (capped at 7 shown), outlined for the rest; if today is part of the streak, its dot gets a pulsing ring animation.

### 4.8 Badge catalog — exact unlock conditions

| Badge | Label | Unlock condition (shown on hover) | Category |
|---|---|---|---|
| FIRST_LESSON_DONE | First Lesson Done | Complete 1 scale | Course |
| SCALE_MASTER | Scale Master | Complete 2 scales | Course |
| RHYTHM_SPECIALIST | Rhythm Specialist | Complete 4 scales | Course |
| CHORD_MAESTRO | Chord Maestro | Complete 5 scales | Course |
| COURSE_GRADUATE | Course Graduate | Complete all 6 scales | Course |
| FIRST_FRIEND_ADDED | First Friend Added | Add your first friend | Social |
| COMMUNITY_CATALYST | Community Catalyst | Have 5+ friends | Social |
| ACTIVE_PRACTICE_PARTNER | Active Practice Partner | "Practice together with a friend regularly" | Social — **defined but intentionally never awarded** (no real mechanic exists to measure it honestly; leave it permanently locked rather than fake-award it) |

Awarding is idempotent (re-checking and re-awarding an already-earned badge is a harmless no-op). Course badges re-check on every scale completion; social badges re-check on every friend-request acceptance; streak badges re-check on every streak update. **All milestones up to the current count get awarded at once**, not just the newly-crossed one (e.g. completing scale #4 for the first time awards FIRST_LESSON_DONE, SCALE_MASTER, and RHYTHM_SPECIALIST together if they weren't already earned).

**Badge grid (on the profile page):** grouped into 3 sections in order — Course completion, Practice streaks, Social. ### 4.9 The interactive scale-explorer tool (below the course player)

A companion tool per scale showing:
- A variant switcher (only if a scale has more than one named variant, e.g. Bati Major/Minor/Lydian).
- A 12-key selector (the exact 12 keys the curriculum book uses: C, G, D, A, E, B, F#, Db, Ab, Eb, Bb, F).
- A "transposition dashboard": the scale's formula spelled out as note chips in the selected key, plus a full reference table showing all 12 keys' spellings at once (current key highlighted).
- A "native chords" panel: each scale's book-defined chord list (roman numeral + chord symbol + spelled notes), rebuilt live for whichever key is selected.

**Important:** correct note spelling must follow standard theory convention exactly — a flat-numbered scale degree (b3, b5, b7, b9) is always spelled as a flatted letter name, never its sharp enharmonic equivalent, and vice versa for sharp-numbered degrees (#4, #5, #9). This determines which specific letter+accidental combination is "correct" at each of the 12 keys, and it's core to the product's value proposition (the physical curriculum book is built entirely around getting this right).

Full per-variant native chord data (degree, chord quality, roman-numeral label) for all 10 scale variants across the 6 chapters — request this from the original repo's `src/lib/scale-content.ts` if rebuilding the explorer tool in detail; it's extensive reference data best transcribed directly rather than re-typed here.

## 5. Messaging &amp; Social

### 5.1 Friends system — `/friends`

If the signed-in user has no username set yet, the whole page collapses to just: "Set a username first" / "Needed so other students can find and add you." + a button to the profile page.

Otherwise, sections top to bottom (each with its own empty state, several sections hidden entirely when empty rather than showing "no results"):

- **Find people**: search box ("Search @username", min 2 chars, button "Search" → "Searching…"), results list with "Add friend" buttons (turn to disabled "Sent" locally after clicking).
- **Friend requests** (only shown if any exist): each row has "Accept" (amber) / "Reject" (outline) buttons, no confirmation.
- **Sent requests** (only shown if any exist): each row shows a static "Pending" label — no cancel/withdraw option exists.
- **Friends (N)**: empty state "No friends yet — search above to find people." Each row: "Message" (→ opens that conversation) / "Block" (no confirmation).
- **Blocked** (only shown if any exist): "Unblock" button per row.

**Business rules:** sending a request to someone who already sent you one auto-accepts instead of duplicating. Blocking someone automatically un-friends them (rejects any pending/accepted request between you). Unblocking does NOT restore a prior friendship — they'd need to re-request.

### 5.2 Messages — `/messages`

**Zero state** (no friends AND no groups at all): just a line of text pointing to the Friends page.

**Normal layout:** 3-column-feeling but really 2 panes — a sidebar (pinned conversations grid, then regular conversation list, then group list) and an active-thread pane. On mobile, these collapse into a single view that swaps between list and thread (never both visible at once).

**Sidebar contents, top to bottom:**
- **Pinned grid**: big circular avatars in a 3-column grid; shows a typing indicator OR a truncated last-message snippet as a badge; small unpin button on each.
- **Conversation list**: avatar, name, unread-count badge ("9+" cap), typing indicator or last-message preview, a pin toggle button.
- **Group list**: a "+ New group" button in the section header; each group row shows a generic group icon, computed title (custom name → else comma-joined member names → else literal "Group"), unread badge, and a "{sender}: {message}" preview.

**Chat window:** header shows name + typing indicator or username; message bubbles (mine = right-aligned amber, theirs = left-aligned dark); relative timestamps only ("just now" / "{n}m" / "{n}h" / "{n}d" — never an absolute date); single-line composer with a 2000-character cap; "Send" button. No edit/delete/react on sent messages. Capped at the most recent 100 messages, no pagination.

**Group chat window:** same bubble/composer pattern, plus sender name+avatar shown above each incoming message (not for your own). Header shows member count and a two-step "Leave" confirmation (inline swap: Leave → Cancel/"Leave group" → leaving removes you and, if you were the last member, deletes the whole group). **No other group management exists** — no rename, no add/remove member, no mute; membership is fixed at creation.

**New group panel** (slide-over from the right): optional group name field, a checklist of your friends (friends with no username set are disabled — can't be added), "Create group (N)" button.

**Live-feeling behavior (poll-based, not websockets):** conversation/group lists refresh every 15 seconds; an open thread refreshes every 2.5 seconds. Play a short two-note chime sound when a new message arrives from the other party while a thread is open (never on the very first load of a thread). A typing indicator appears while the other person is actively typing (based on recency of a "typing" ping, not a persistent flag) and disappears automatically after a few seconds of inactivity.

**Important: new messages do NOT create notification-bell entries** — only the Messages badge count and, if the recipient opted in, an email. Keep these two systems visually separate.

### 5.3 Validation rules

Message body: 1–2000 characters, can't message yourself, must be friends, can't message a blocked/blocking relationship. Group creation: 1–23 friends + yourself (24 max), every named member must already be a friend.

### 6.1 Pricing

5. Payment now sits in PENDING_REVIEW until an admin approves or rejects it (§7.4).

| Status | Student sees |

| REJECTED | Red banner with the reason + "Resubmit payment" button |

## 7. Admin Panel

### 7.1 Access control — three independent layers, all required

1. **Route-level**: any `/admin/*` URL redirects a non-admin (or logged-out user) away before rendering.
2. **Layout-level**: the admin section's shared layout re-checks role server-side.
3. **Action-level (the real enforcement)**: **every single admin mutation re-checks the caller's role itself**, independent of whether the page around it rendered — because in a real backend, a mutation endpoint is a separate entry point that a UI-layer check alone cannot protect. Never rely on "the page already checked" for a write action.

### 7.2 Admin nav (exact order): Overview → Payments → Bookings → Students → Lessons → Users.

### 7.3 Overview (`/admin`)

4 stat cards: **Total users**, **Curriculum access** (count with the $99 unlock), **Pending payments** (highlighted amber when &gt;0), **Total revenue** (sum of all verified payment amounts — the only revenue metric tracked). 3 quick links: "Review pending payments ({n}) →", "Lesson bookings →", "Manage users →". A "Module health" table — one row per scale showing how many users have unlocked it, how many have completed it, and a computed completion percentage.

### 7.4 Payments queue (`/admin/payments`)

Filter pills: Pending (default) / Verified / Rejected / Awaiting / Expired / All. Each card: item description, submitter, amount, status badge, sender name, reference code, submitted date, optional note. Buttons only on PENDING_REVIEW items — **"Approve"** (no confirmation, one click, → "Approving…") and **"Reject"** (reveals an inline required-reason textarea → "Cancel" / "Confirm reject" → "Rejecting…"). Applies the effects from §6.7 automatically.

A background sweep should auto-expire any AWAITING_TRANSFER payment older than 7 days (never touches PENDING_REVIEW — once a student submits, it can't silently vanish).

### 7.5 Bookings queue (`/admin/bookings`)

Filter pills: Scheduled (default) / Completed / Canceled / All. Each card: student, "{Online/In-Person} · {date/time}", email, notes, status. Buttons on SCHEDULED only: **"Mark completed"** (no confirmation, triggers a brief success-glow effect) and **"Cancel (refund credit)"** (inline optional-reason textarea, refunds the credit automatically on confirm).

### 7.6 Students queue — class registrations (`/admin/students`)

Filter pills: Pending (default) / Approved / Rejected / All. Each card: registrant info, instrument+skill, contact info, notes. Same approve (no confirm)/reject (required-reason textarea) pattern as payments — approving/rejecting emails the registrant directly at the address they typed on the public form (not necessarily their account email, if different).

### 7.7 Users management (`/admin/users`)

Live-search by name/email (no submit button, updates as you type). Each user row: name, email, role badge, curriculum-access badge, one small chip per scale (S0–S5) showing locked/unlocked/completed — **clickable to toggle that individual scale's unlock state** — plus two buttons: "Make admin"/"Remove admin" and "Grant curriculum"/"Revoke curriculum" (both instant, no confirmation). **Guard rail: an admin cannot remove their own admin role from this panel** (must be done by a different admin). Promoting someone to admin sends them a notification: "You've been granted Admin access — Your account now has Admin permissions — you can manage payments and users from the Admin panel."

### 7.8 Lessons management — course content upload (`/admin/lessons`)

This is the admin upload tool for the video/PDF course content described in §4.5–4.6. **Distinct from the live-lesson booking system (§6.6/§7.5)** — same word, different feature; keep them clearly separate in the UI and in any code/data naming.

- If object storage isn't configured, an amber banner says so and the upload button is disabled (existing lessons can still be reordered/deleted).
- A pill per scale (0–5) to pick which chapter you're managing.
- "Upload a lesson" toggles a form: Title (required), Description (optional), a file picker accepting video or PDF (required) — client detects type from the file automatically. **A real progress bar during upload** (this matters — the original app specifically called out that a spinner with no percentage feedback "reads as broken, not as working" on a large video file).
- Below the form: the existing lesson list, each showing position number, type badge, title, description, file size + duration (video only). **Up/down arrow buttons to reorder** (no drag-and-drop). **Delete with an inline confirm step** (Delete → Cancel/"Confirm delete" swap, no modal).

**If your storage layer requires large-file upload (video), architect it as direct-to-storage from the browser** (a short-lived signed upload URL issued by the server, with the actual bytes going straight from the browser to storage) rather than routing the file through your app's own backend — this avoids common serverless request-body-size limits and lets a real upload-progress percentage be shown, which a server-relayed upload typically can't provide.

### 7.9 Cross-cutting admin UI conventions to match everywhere

- Every "destructive or requires-explanation" action (reject, cancel) expands **inline within the same card** into a textarea + Cancel/Confirm pair — never a modal/dialog popup.
- Every "simple positive" action (approve, mark completed, grant) is a single click with **no confirmation step** at all.
- Every busy button shows a present-participle label ("Approving…", "Saving…", "Uploading…", "Deleting…").
- Empty-list states are a plain centered muted message, never blank.

## 9. Design System — "Dynamic Glass"

### 9.1 The core idea in one paragraph

Every screen sits on a full-bleed, warm/desaturated, cinematic photograph (piano keys, guitar, violin, sheet music, vinyl — never a stock-photo-looking or brand-logo-visible image). A dark vertical vignette (fully opaque near-black at the very top and bottom, translucent in the readable middle) sits over every photo for text contrast, with a very soft warm amber glow diffused into the opaque bands so it reads as light/smoke rather than a hard fade. Frosted "real glass" panels float on top of that: heavy blur, a diagonal light-catching gradient fill, a **directional** border (brighter on the top/left, as if lit from the upper-left, dimmer on bottom/right), and a layered shadow (a soft drop shadow for lift, a tight contact shadow for grounding, and a thin inset highlight along the top inner edge). Exactly one accent color (amber) is used sparingly for CTAs, active states, prices, and glows — never any other warm hue as a substitute. One elegant serif face for every heading/title, one clean sans face for everything else. Motion is spring-physics throughout with a consistent "signature" feel, not ad-hoc per component.

### 9.2 Color

- Base/background: near-black navy (`#020617`).
- Primary text: near-white; secondary text: light gray (dimmer than primary, used specifically for text sitting over a photo, since it needs more contrast headroom); tertiary/meta text: a darker gray, **only ever used over the flat background, never directly over a photo**.
- **The one accent color: amber `#fbbf24`** (hover/emphasis variant `#fcd34d`) — used for every CTA, active nav state, price, badge, and glow tint in the entire app. No gold/orange/yellow substitutes anywhere.
- Positive state (success, discounts, verified): emerald green. Negative state (errors, rejections): red.
- Dark mode only — there is no light theme.

### 9.3 Typography

- Headings/titles: an elegant, high-contrast serif (the original uses Playfair Display, restricted to medium/semibold/bold weights only — no light/regular serif anywhere, even for small utility panel titles).
- Body/UI text: a clean grotesque sans (the original uses Inter).
- A recurring "eyebrow" label pattern above section headings: small, uppercase, wide letter-spacing, amber, medium weight — used constantly throughout the app as a section/category marker.

### 9.4 The glass material recipe (reproduce as closely as your platform's styling system allows)

- **Default glass panel**: rounded corners (~16px), heavy background blur, a diagonal (top-left to bottom-right) white gradient fill fading from ~9% to ~3% opacity, a border split into 4 different opacities per side (brightest top, dimmer left, dimmest right/bottom — simulating an upper-left light source), and a 3-layer shadow: a big soft drop shadow for lift off the page, a tighter contact shadow for grounding, and a thin inset highlight along the top inner edge that reads as a catch-light.
- **Elevated glass panel** — reserved for **exactly one** element per screen (the single primary/highlighted card — a pricing card, a quiz-passed result, a hero CTA): even heavier blur, a brighter top/left border, the background gradient itself shifts warm (tinted amber in its fill, not just plain white), and an additional very soft inset amber glow bleeding through from inside the glass. Using this treatment twice on one screen defeats its purpose — it should always read as "the one that matters."
- **Pill/chip glass** — for nav pills, tags, small badges: lighter blur, fully rounded, a single uniform border (no directional split needed at that size).
- **Dense/data-heavy surfaces** (admin tables, forms): stack extra blur on top of the base recipe so the photo behind stays pure atmospheric texture and never competes with data for attention.
- **Primary-button sheen effect**: a diagonal band of light that sweeps across a button on hover (parked off-screen at rest, animates across over ~0.6s with an ease-out curve) — apply to the single primary action per form/card only, not every button. Must fully disable (not just skip) under reduced-motion preference, rather than snapping instantly.
- **Scrims**: three strength variants (light / standard / dense) for different contexts (marketing hero wants more photo showing through; admin/dense surfaces want the photo pushed further back as pure texture). All must guarantee real text-contrast compliance (WCAG AA: 4.5:1 body text, 3:1 large text) against the scrim, not the raw photo.

### 9.5 Photography

Photos are assigned per **context**, not per page — e.g. every authenticated dashboard page shares one fixed backdrop photo, every auth screen (login/register/forgot/reset/verify) shares one, so navigating within a context never flashes a different image. Marketing pages get one distinct photo per section instead, since those are meant to feel like a scrolling journey. All images warm-graded, desaturated, cinematic, no visible logos/brands/text.

### 9.6 Motion signature (spring physics values, for platforms that support tunable spring animation)

- **Standard entrance** (cards, list rows, sections fading/rising in): spring stiffness ~240–260, damping ~24–26. This is the default for almost everything.
- **Overlay/sheet/modal entrance** (things sliding in from an edge — bottom sheets, side drawers, dialogs): a snappier, less bouncy spring — stiffness ~300–340, damping ~28–34.
- **Multi-step wizard transitions** (auth steps, onboarding steps, quiz steps): stiffness ~300, damping ~30.
- **Celebratory/bouncy pops** (a badge unlocking, a small checkmark icon): a deliberately bouncier spring — stiffness ~260–300, damping ~15–18 — reserved specifically for reward moments, distinct from the calmer standard entrance.
- **Staggered lists**: children animate in with a small delay between each, roughly 0.06–0.12 seconds apart (denser lists use the smaller end, sparser hero-level groups use the larger end).
- **A one-shot "success" glow**: an inset amber glow that pulses twice (fade in → out → in → out) over about 1.1 seconds total, used identically across every "you did it" moment in the app (quiz passed, section completed, payment confirmed, booking completed) — one shared visual language reused everywhere rather than a bespoke animation per feature. Must render as `null`/nothing under reduced-motion, not a static substitute.
- **A count-up number animation**: 0 → target value over ~0.7 seconds, ease-out, rounding to the nearest whole number per frame — used for the quiz score reveal.
- **Global reduced-motion safety net**: respect the OS/browser's reduced-motion preference everywhere motion exists — this should be a blanket default (auto-snap every animation to its end state) layered under any component-specific checks, not an afterthought.

### 9.7 Layout rhythm

- Standard density: card padding in the 20–32px range, grid gaps 12–16px.
- Marketing page sections run tall (112–224px vertical padding) so full-bleed photography has room to actually read as environment, not a cramped strip.
- Max content widths: widest for marketing grids, narrower (copy-width) for text-focused sections, narrowest for dashboard forms.
- Standard corner radius ~16px for glass surfaces, fully round for pills/badges/avatars, larger top-only rounding for bottom sheets.

### 9.8 Accessibility/consistency checklist (treat as non-negotiable acceptance criteria)

- No emoji-as-icon anywhere — real icon glyphs only, consistent stroke weight, no icon-font-vs-SVG mixing.
- Every clickable element gets a pointer cursor and a 150–300ms hover transition.
- Visible focus rings for keyboard navigation everywhere — never strip an outline without providing a replacement focus-visible treatment.
- No horizontal scroll at narrow (≈375px) viewport widths.
- Headings always in the serif face; body text always in the sans face — no exceptions, even at small utility scale.
- The accent color is amber, full stop, everywhere in the app.

## 10. Navigation Shell

**Desktop** (wider viewports): a slim (~96px) vertical icon rail, translucent glass floating over the app-shell photo backdrop, fixed to the left edge. Order, top to bottom: Roadmap (dashboard) → Lessons → Friends → Messages → *(Admin, admins only)* → *(divider)* → Profile → *(spacer pushes the rest to the bottom)* → Settings → About → Sign out. Each item is an icon + tiny label stacked vertically. Active state = soft amber-tinted background chip; inactive = muted; hover = subtle brighten. Messages carries an unread-count badge ("9+" cap).

**Mobile** (narrow viewports): the rail disappears entirely, replaced by a 5-tab bottom bar: Roadmap, Friends, Messages (same badge), Profile (kept as its own permanent tab — never buried in an overflow menu, since reaching it quickly matters), and "More" (opens a bottom sheet containing Lessons, Admin if applicable, Settings, About, Sign out — items that didn't fit as top-level tabs). The "More" tab itself highlights amber whenever the current page is one of the items living inside that sheet, even while the sheet is closed.

**Generic slide-over drawer** (for any secondary detail view pushed over the current screen): full-screen on mobile, a right-anchored capped-width drawer on desktop; closes via Escape, backdrop click, or a back-arrow header button; slides in from the right with the "overlay" spring from §9.6.

## 11. Infrastructure Notes (translate to Base44's native equivalents)

These describe *why* certain architectural choices were made in the original build — useful context even though Base44 will implement its own version of each:

- **Object storage for lesson video/PDF uploads**: files go directly from the admin's browser to storage via a short-lived signed upload URL, bypassing the app's own backend entirely — done specifically because serverless backends often cap request body size at a few MB, which would break large video uploads if routed through them. If Base44's file-upload primitive already handles large files without this concern, you don't need to replicate the presigned-URL pattern — just make sure large video uploads actually work and show real progress feedback.
- **Transactional email**: every code/notification email goes through one shared send function and one shared HTML template (see §3.2 for exact copy). A development fallback that just logs the email instead of sending it (when no email-provider credentials are configured) is a nice-to-have but not essential if Base44 has its own dev/preview email handling.
- **Payment collection**: manual Zelle transfer + human admin review, with **no payment-processor integration anywhere** — see the decision note in §0 about whether to keep this exact flow or swap to a real processor.
- **Database**: a single relational schema (Postgres in the original) is sufficient — nothing here needs a specialized data store.
